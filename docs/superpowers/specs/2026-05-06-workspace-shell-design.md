# 编辑器工作台壳页设计

## 目标

为现有项目新增一个统一的“编辑器工作台”入口页，用来承载多个平台编辑器。

第一阶段先把微信编辑器挂进工作台右侧，让页面不再出现大块无效空白；同时预留小红书编辑器入口，但本次不实现小红书正文功能。

## 用户已确认的方向

本次需求已经明确以下约束：

- 当前重点不是继续做单独的效果展示页主入口，而是先搭一个工作台壳页
- 左侧作为平台切换区，不再浪费为空白区域
- 左侧第一项先挂 `微信编辑器`
- 左侧第二项预留 `小红书编辑器`
- 点击左侧 `微信编辑器` 后，右侧区域直接显示微信编辑器界面
- 右侧显示方式采用 `iframe`，而不是把多个编辑器硬拼到同一页
- 微信编辑器自己的工具栏继续保留在微信编辑器页面内部
- 小红书编辑器本次先不做真实功能，只留入口和占位状态
- 后续每个平台都可以拥有自己独立的 `html / css / js`

## 页面定位

这个新页面不是某一个平台的编辑器本体，而是一个“平台编辑器工作台”。

它只负责两件事：

1. 在左侧提供平台切换入口
2. 在右侧承载当前被选中的平台编辑器页面

也就是说，工作台负责切换，具体平台页面负责编辑。

## 总体架构

建议新增一个总入口页面，例如：

```text
在线微信编辑器/
├─ workspace.html
├─ Markdown编辑器_蓝色主题 - Copy.html
├─ rules.html
├─ demo.html
├─ styles/
│  └─ editor.css
└─ scripts/
   └─ editor.js
```

当前阶段结构建议如下：

- `workspace.html`：新的工作台壳页
- `Markdown编辑器_蓝色主题 - Copy.html`：继续作为微信编辑器页面使用，先不强制重命名
- `rules.html`：微信编辑器对应的规则页
- `demo.html`：微信编辑器对应的效果展示页
- 小红书编辑器页面后续再新增

## 信息架构

### 左侧平台切换区

左侧区域从原本的无效空白，改造成固定的平台入口区。

第一阶段只放两项：

- `微信编辑器`
- `小红书编辑器`

其中：

- `微信编辑器` 为默认选中项
- `小红书编辑器` 为未完成入口，先展示占位状态

左侧切换区不承担复杂说明功能，不放规则、不放预览、不放编辑器操作按钮。

### 右侧主承载区

右侧是页面的主工作区，使用一个大尺寸 `iframe` 承载当前平台页面。

默认状态：

- 页面加载后，右侧直接展示微信编辑器

切换逻辑：

- 点击左侧 `微信编辑器`，右侧 `iframe` 显示微信编辑器页面
- 点击左侧 `小红书编辑器`，右侧显示小红书占位页或占位状态

## 为什么采用 iframe

本次明确采用 `iframe`，而不是把不同平台编辑器直接拼进一个大 HTML。

原因如下：

1. 每个平台未来都需要自己的规则、样式、脚本和行为逻辑
2. 微信与小红书在编辑目标和展示风格上天然不同
3. 用 `iframe` 可以把平台边界隔离干净，避免后期 JS/CSS 互相污染
4. 后续新增平台时，只需要在左侧加入口，并在右侧指向新的独立页面

所以这里的核心不是“单页模式切换”，而是“工作台承载多个独立平台页面”。

## 布局策略

### 桌面端

工作台整体采用左右结构：

- 左侧为窄栏平台区
- 右侧为主编辑承载区

目标不是做成后台控制台，而是让右侧编辑器区域尽可能铺满、尽可能像真正主工作区。

左侧应满足：

- 宽度稳定
- 不喧宾夺主
- 入口清楚
- 当前选中态明确

右侧应满足：

- 占据大部分宽度
- `iframe` 尽量铺满高度与宽度
- 不出现明显的大块无效留白

### 移动端

移动端不需要继续保持左右窄栏布局。

建议切为：

- 顶部为平台入口区
- 下方为 `iframe` 承载区

这样可以避免手机上左栏挤压正文空间。

## 左侧平台栏设计原则

左侧平台栏的作用是“切平台”，不是“展示平台细节”。

建议内容非常克制：

- 一个简短标题，例如 `平台选择`
- 两个入口项
- 必要时加一句小字说明，例如 `后续可扩展更多平台`

视觉上应做到：

- 微信入口默认高亮
- 小红书入口可见但弱一些
- 选中项一眼可见
- 不使用过重的大卡片堆叠感

左栏中明确不放：

- 规则按钮
- 打开文件按钮
- 保存按钮
- 复制 HTML 按钮
- 预览按钮

这些都属于具体平台页面，而不属于工作台壳页。

## 右侧微信编辑器接入原则

由于右侧会通过 `iframe` 装载微信编辑器，因此微信编辑器页面本身不再是整个系统的入口，而是被工作台承载的子页面。

这意味着微信编辑器需要遵循以下原则：

### 1. 保留自己的工具栏和行为

当前微信编辑器已经拥有自己的工具栏与操作：

- 规则
- 打开文件
- 保存 Markdown
- 复制 HTML
- 预览
- 清空

这些继续保留在微信编辑器页面内部，不上提到工作台全局。

### 2. 继续保持独立可打开

虽然它会被嵌入 `iframe`，但微信编辑器页面仍应支持直接双击打开。

这样有利于：

- 单独调试页面
- 单独查看页面
- 后续独立维护

### 3. 做一轮嵌入式优化

当前微信编辑器存在的最大观感问题之一，是页面内部没有充分吃满可用空间，导致明显空白。

在进入工作台后，微信编辑器页应朝以下方向调整：

- 收紧不必要的外围空白
- 让编辑区更充分使用横向空间
- 让页面看起来更像“主工作区”，而不是“卡片里再放一个编辑器”

### 4. 微信的辅助页面继续归属于微信分支

当前已有的：

- `rules.html`
- `demo.html`

都继续视为微信编辑器分支下的页面。

也就是说，从微信编辑器内部点开的规则页和效果展示页，仍然服务于微信平台内容，而不是变成工作台全局通用页面。

## 小红书入口的当前边界

本次先不实现真实的小红书编辑器。

第一阶段只完成：

- 左侧出现 `小红书编辑器` 入口
- 点击后右侧显示一个占位状态，明确告诉用户该页面后续接入

当前不包含：

- 小红书正文编辑区
- 小红书专属规则
- 小红书样式系统
- 小红书 HTML 输出逻辑

这样可以先把工作台结构搭起来，再逐步接入第二个平台。

## 视觉方向

### 工作台壳页

工作台壳页应当比当前微信编辑器更“容器化”，更像一个承载多个平台的稳定框架。

视觉关键词：

- 清楚
- 稳定
- 克制
- 导航轻、工作区重

### 左侧

左侧不应继续大片留白，也不应做得太花。

它更像一个非常简洁的平台切换栏：

- 背景可以与右侧略有区分
- 选中项有明确高亮
- 不做复杂装饰

### 右侧

右侧的视觉重点应当让位于被加载的微信编辑器页面。

也就是说：

- 工作台本身不要再给右侧加重卡片壳
- `iframe` 容器尽量干净
- 真正的视觉主角应是里面的微信编辑器内容

## 交互原则

工作台的交互应非常单纯：

1. 打开工作台
2. 默认看到微信编辑器
3. 点击左侧可切平台
4. 不打断当前右侧页面的内部功能

换句话说，工作台负责“切换入口”，平台页面负责“具体工作”。

## 测试与验证

完成实现后，需要重点验证以下内容：

1. 打开 `workspace.html` 后，默认左侧高亮 `微信编辑器`
2. 页面初始状态下，右侧已直接显示微信编辑器
3. 左侧区域不再是无效空白
4. 右侧 `iframe` 区域能充分铺满可用空间
5. 微信编辑器内部工具栏仍然正常工作
6. 微信编辑器内部的规则页、效果展示页、预览等逻辑不受工作台影响
7. 点击左侧 `小红书编辑器` 后，右侧能显示明确占位状态
8. 手机宽度下左侧平台区会切换为更适合小屏的布局

## 实现边界

本次只完成工作台壳页与微信编辑器接入，不进行以下工作：

- 不重写微信编辑器核心功能
- 不实现真实小红书编辑器
- 不做跨 iframe 的复杂通信
- 不做平台间内容同步
- 不做登录、项目管理、多文档系统

## 结论

这次改造的本质，不是再往当前微信编辑器页面里塞功能，而是先搭一个能长期扩展的平台工作台壳。

左边负责切平台，右边负责承载平台自己的完整页面。微信先接上，小红书先占位。这样你可以先看微信编辑器在新结构里顺不顺，再一步一步把第二个平台接进来。
